## Key Features

- **Seven transitions, answered on four axes each** — what is read, what is written, by whom, and
  what an interrupt leaves behind — with a machine-checkable `- T<n> resolved:` line per section.
- **Six recorded limits**, each classified `design` or `mixed` and each argued from a named
  constraint rather than asserted. A recorded limit counts as a finished transition; an asserted
  one does not.
- **A constraint set the model may not relax**: additive-only `init`, no tool-side deletion, no
  remote, zero runtime dependencies.
- **PRD-034 blocked by construction** until an owner acceptance names this document, with no
  partial approval — the answers interlock, so a subset cannot be released.

## Technical Implementation

The model was written against the shipped code, not against the design that preceded it:
`core/run/prompts.ts` (render, adapters, banner, `generatedPaths`), `core/run/init.ts`
(`planPrompts`, `promptsConfigBlock`, `initWorkspace`'s `wx` contract), `cli.ts`'s `--prompts`
branch, and `core/config/defaults.ts`.

Three findings came out of that reading and shaped the answers:

1. **The banner is not universal.** Store files and the `claude-code` / `cursor` adapters carry
   `<!-- GENERATED by provegate <version> … -->`; the `codex` snippet carries none, knowingly. The
   one file an adopter is expected to paste by hand is the one with no provenance — so
   content-based discovery, which T4 and T5 rest on, has a hole exactly there.
2. **Adapters embed store paths in their content.** Renaming `prompts.dir` leaves
   `.claude/commands/prd-*.md` pointing at the abandoned tree, and the reinstall skips them because
   they already exist.
3. **Activation is a precondition, not a step that can lag.** `prompts.enabled` defaults to
   `false` and the command exits non-zero before planning anything, so a store cannot precede its
   config block.

## Review

Round 1 returned **fail**, and the three HIGH findings were all in the document's substance:

- The Vocabulary claimed the banner was universal; the `codex` snippet has none. The premise was
  load-bearing for three transitions.
- T3, titled *Upgrade with one deliberately edited file*, answered the **install** case. Under T2's
  own upgrade mechanism — the adopter deletes the reinstall unit — the edit is destroyed by
  default, and if spared it is pinned at the old version permanently.
- T6's limit ("no command can report the store's location") was refuted by T5 on the same page.

Two more were failures of evidence rather than design, and both were mine: the task ledger cited a
turbo cache hit as proof of §6, which it cannot be, and the durable learning claimed five rounds
where PRD-029 ran eight and ended at 8.35 PASS — attributing the turn to a state model when the
readiness record attributes it to a scope cut plus a restatement sweep.

All nine were fixed in the files, none waived. Round 2 passed with one new LOW, itself also fixed:
the limits table justified a classification with temp-then-rename, which `rename(2)` makes unsafe
under the additive-only constraint.

**The reviewer was a fresh same-family session with zero implementation context — the method's
documented fallback, not its default.** A different model family would be stronger evidence. This
session wrote the PRD, scored it, planned it and authored the deliverable, so the review is the
only outside reading this document has had.
