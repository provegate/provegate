# Prompt Store State Model

> **Owner**: owner · **Status**: Revision 1 owner-approved 2026-07-28 (`_state/acceptances.json`, PRD-030, items 4.1 T1–T7 and 4.3); **Revision 2 awaiting owner approval** — supersedes Revision 1's banner-uniqueness claim, consequences enumerated in the closing section · **Created**: 2026-07-28
> **PRD**: [prd-030-prompt-store-integrity.md](../../_prds/completed/prd-030-prompt-store-integrity.md)
> **Consumed by**: PRD-034, whose functional requirements are written against this document
> and are blocked until it is approved.

The complete set of state transitions a generated protocol store can undergo, and the actor
performing each. Written against the store **as PRD-029 shipped it**, not against any design
that preceded it.

---

## Constraints

Every transition below is answered under these four, and none may be silently relaxed:

1. **`gate init --prompts` is additive-only.** `wx` writes; an existing path is reported as
   skipped; nothing is ever overwritten. `planPrompts` deliberately carries no preflight and no
   mismatch refusal, so the promise holds for every caller of `initWorkspace` rather than being
   carved out for this one.
2. **No command deletes an adopter's file.** Removal is a human action, in every transition.
3. **No code path reaches a git remote.**
4. **`packages/provegate` takes zero runtime dependencies.**

A transition with no honest answer inside these four **records the limit** instead of acquiring
a mechanism. A recorded limit is a finished transition.

---

## Vocabulary

- **Store** — the rendered protocol files under `config.prompts.dir`.
- **Adapters** — generated pointers derived from `config.prompts.adapters`. Two of the three
  destinations live **outside** the store directory: `.claude/commands/prd-<phase>.md` and
  `.cursor/rules/prd-workflow.mdc`. The `codex` adapter writes
  `<dir>/AGENTS.md.provegate.snippet`, which the adopter pastes themselves.
- **Generated set** — store ∪ adapters; the map `generatedPaths()` returns and
  `gate init --prompts` prints. **This is the reinstall unit**, and it is wider than the store
  directory.
- **Banner** — `<!-- GENERATED by provegate <version> — \`gate init --prompts\`. Do not edit. … -->`,
  written by `bannerFor` for store files (below the frontmatter where the format requires line 1)
  and inlined for the `claude-code` and `cursor` adapters. `<version>` is the installed
  package's, or the literal `unknown` when the manifest cannot be read.

  **It is not universal, and every answer below that leans on it carries the exceptions —
  there are TWO unbannered generated paths, not one (Revision 2).** The `codex` adapter's
  `<dir>/AGENTS.md.provegate.snippet` is emitted as `## Phase protocols` plus the phase
  table and **carries no banner and no version** (`core/run/prompts.ts::renderAdapters`);
  PRD-029's review recorded that omission as knowingly accepted. **And the store's own
  `prompts/PLACEHOLDERS.md` is copied verbatim with no banner and no substitution — a
  deliberate `verbatim` disposition (`core/run/prompts.ts:656-661`): the registry documents
  the very tokens substitution would consume, so bannering or rendering it would destroy
  what it exists to say.** Revision 1 claimed the codex snippet was unique; an independent
  reading of the shipped renderer against `generatedPaths()` refuted that. The store
  `README.md` carries a shorter one-line banner inlined by `storeReadme` rather than the
  `bannerFor` form. So the provenance signature covers the store **minus PLACEHOLDERS.md**
  and two of the three adapters.

  **What an unbannered PLANNED path still permits (Revision 2's structural consequence):**
  both unbannered paths are members of `generatedPaths()`, so **divergence detection by
  byte comparison against a fresh render works for them exactly as for every planned
  path**. What is lost is **attribution only** — with no banner there is no recorded
  version, so a byte difference cannot be split into "package upgraded" (stale) versus
  "edited at the current version" (modified). The same holds for any planned file whose
  banner a human has stripped or mangled: detectable by bytes, unattributable by banner.
  A classification over planned paths must therefore be total in three arms — bytes
  equal; bytes differ with a parseable banner (attributable); bytes differ or banner
  unparseable/absent (unattributable) — and content-based discovery of UNPLANNED files
  (T4/T5/T6) finds only the bannered ones; both unbannered paths, and any stripped file,
  are invisible to it.
- **Activation record** — the `prompts` block in `workflow.config.json`. The tool prints it
  (`promptsConfigBlock`); the adopter pastes it. The installer never edits that file, and
  `prompts.enabled` defaults to `false`.

**The banner is the only durable per-file provenance that exists today — with the gap named
above — and the config is the only durable locator.** Every answer below is constrained by that
pair, because there is no third place where state lives: PRD-029 writes no receipt.

## Transitions

### T1 Install into a repo that already has a config

**Question.** How is activation recorded when no file may be edited?

`gate init --prompts` cannot write `workflow.config.json` — the installer's additive-only
contract means an existing path is skipped, and this file always exists by the time prompts are
installed. `promptsConfigBlock` therefore **prints** a complete block, every required token
present and unset as `null`, followed by each token's meaning.

**Answer.** Activation is recorded by the **adopter**, by pasting the printed block, and the
paste is a **precondition of the store existing rather than a step that can lag it**: the
command reads `config.prompts.enabled` before planning anything, and on `false` — the shipped
default — it prints the block and exits non-zero having written not one file. There is no
machine-written activation record and there should not be one: the config is the adopter's file,
and the installer's promise not to touch it is worth more than the convenience.

A store on disk with no `prompts` block is therefore **not** reachable by installing; it is
reachable only by installing and then removing the block, which is T6's transition, or by
copying files in by hand.

**The installer writes more than the generated set.** The prompt plan is passed to
`initWorkspace` as extra actions, and that function always plans the base scaffold too — so a
first run can also create `gates.manifest.json` and the artifact directories. Those writes are
additive-only like every other, but they are **outside the set the command prints as the
reinstall unit**, which means the recovery instruction below does not cover them.

An interrupted install leaves a **partial generated set** with no marker distinguishing it from
a complete one, because the writes are file-by-file with no transaction and no manifest.
Recovery is the reinstall unit: delete every printed path, run again. The set to delete is
knowable only from the command's printed output or from a full re-render.

- T1 resolved: reads=config.prompts.enabled+workflow.config.json+package-corpus writes=generated-set-plus-base-scaffold actor=installer-writes-files/adopter-writes-config interrupt=partial-set-indistinguishable-recover-by-delete-and-reinstall

### T2 Upgrade

**Question.** What changes, who applies it, and how does the process terminate?

A newer package renders different bytes for the same paths. `init --prompts` cannot deliver
them: every path exists, so every write is skipped and the command reports success. **The
repository keeps running the old protocol while the install reports green.**

**Answer.** What changes is decided by comparing a re-render against disk — the store is a pure
function of package version and config, so the comparison needs no stored state. Who applies it
is the **adopter**, and the apply mechanism is deletion followed by reinstall: deleting a file
is the consent that the additive-only contract cannot supply, and it puts the irreversible step
with the person who can judge it. Termination is by construction — the reinstall unit is finite
and enumerable (`generatedPaths()`), so the loop is one pass over a known set, not a
convergence.

The banner makes a partial upgrade **visible**: a file at version A next to a file at version B
is a readable state, not an ambiguous one. That is the whole of what the banner buys, and it is
enough to report on — **except for the two unbannered paths (the codex snippet and
`prompts/PLACEHOLDERS.md`, Revision 2)**, which carry no version, so a mixed state including
them is readable everywhere but there. A report has to name those paths as version-unattributable
rather than as current — though their bytes still compare against a fresh render like any
planned path.

An interrupted upgrade leaves exactly that mixed state. It is safe: nothing was overwritten,
nothing was deleted by a tool, and re-running the deletion for the remaining paths resumes it.

- T2 resolved: reads=package-render+on-disk-bytes+banner-version writes=nothing-until-adopter-deletes-then-init-writes actor=adopter-deletes/installer-writes interrupt=mixed-version-set-visible-in-banners-resume-by-repeating

### T3 Upgrade with one deliberately edited file

**Question.** Does the edit survive, and what authority says so?

**Answer — and the answer is different for the two operations the title could mean.**

Against an **install**, the edit survives by construction, and the authority is the
**additive-only contract** — not a rule about edits, not a list, not a flag. `init --prompts`
skips every existing path, so an edited file is untouched for the same reason an unedited one
is. No mechanism needs to know the file was edited in order to spare it.

Against an **upgrade**, it does not. T2 fixes the upgrade mechanism as the adopter deleting the
reinstall unit and running `init` again; the edited file is a member of that unit and is printed
with the rest, so the default path **destroys the edit**. It survives only if the adopter
recognises that path and spares it by hand — and nothing in the system helps them, because an
edit has no representation anywhere. If they do spare it, the file stays at the old version
inside the mixed state T2 describes, **permanently rather than transiently**: no later `init`
will replace it, for the same additive-only reason that let it survive the install.

So the authority answer holds and the survival answer splits: the contract guarantees the edit
against writes, and guarantees nothing against the adopter's own deletion, which is the only
apply mechanism this design has.

What the edit costs beyond that is **detectability**: an edited file at version A and an
unedited file at version A are distinguishable only by re-rendering and comparing. The banner
records provenance, not integrity.

An intentional edit therefore has no representation anywhere today. Whether it should acquire
one, so that a divergence report can separate "someone changed this on purpose" from "this
drifted" — and so that the reinstall unit can be printed with that path marked — is **the one
open design question this model hands to PRD-034**. It is stated as a question rather than
answered here, and its fields are deliberately not sketched, because a record's shape is a
mechanism this document does not own. What the model does fix is the boundary any such record
must respect: **it may suppress a finding, and it may never authorize a write.** Nothing in this
system writes over an adopter's file, and a record that granted that capability would relocate
the deletion consent T2 depends on.

- T3 resolved: reads=on-disk-bytes-only writes=nothing-by-the-tool/adopter-deletes-under-T2 actor=contract-guarantees-against-writes/adopter-decides-at-deletion interrupt=edit-destroyed-or-pinned-at-old-version-inside-T2s-mixed-state

### T4 Add / remove an adapter

**Question.** What happens to the previous file, and who may delete it?

Adapters are rendered from `config.prompts.adapters`. **Adding** one is an ordinary install: the
new destinations do not exist, so they are written; existing ones are skipped.

**Removing** one from the config removes it from the *plan*, and does nothing on disk. The
previous file stays, at its old version, and for `.claude/commands/prd-*.md` it stays where an
agent still reads it. So a removed adapter keeps working, which is the surprising part and the
part worth reporting.

**Answer.** The previous file survives, and **only the adopter may delete it** — constraint 2,
without exception. A tool may name the file as no longer produced; it may not remove it. The
plan and the disk are allowed to disagree, and that disagreement is a reportable state rather
than an error to repair.

The disagreement is discoverable **only by re-rendering with a config that still lists the
adapter**, or by recognising the generated banner in a file the current plan does not produce.
The banner is what makes the second possible, and it is why a report of this state can exist at
all without a receipt.

**The second route does not cover the unbannered paths (Revision 2: both of them).** The
codex snippet and a leftover `PLACEHOLDERS.md` carry no banner, so once abandoned they are
indistinguishable by content from files the adopter wrote. For those paths the first route —
re-rendering with the config that still produces them — is the only one, and if the adopter
has already removed the producing config, nothing recovers them. That is a consequence of
the banner gaps named in the Vocabulary, and it is where a divergence detector built on
this model will have holes unless PRD-034 is told about them here.

- T4 resolved: reads=config.prompts.adapters+render-plan+on-disk-banners writes=new-adapter-paths-on-add/nothing-on-remove actor=installer-writes/adopter-deletes interrupt=partial-adapter-set-recover-by-reinstall

### T5 Rename the store directory

**Question.** How is the old tree discovered, or is it not?

Renaming means editing `prompts.dir` in the config. The next install renders the whole store
under the new directory and writes it — every path is new, so nothing is skipped. The old tree
remains, complete and unreferenced.

Worse, and specific to this system: **the adapters embed store paths in their content.**
`.claude/commands/prd-<phase>.md` contains the literal `<old-dir>/<store-path>`, and the Cursor
rule's table does the same. After a rename those adapters point at the old directory. They are
skipped by the reinstall — they already exist — so they keep pointing there indefinitely. The
result is two complete stores where the agent-facing pointers name the abandoned one.

**Answer.** The old tree is **not discoverable from state**, because no durable record survives
the config edit: the config held the only locator and it now names the new path. It is
discoverable only **by content** — a directory whose files carry the generated banner and which
the current plan does not produce. That is a recognisable signature, and this model records it
as the honest basis for any report, in place of a lookup that cannot exist.

The adapter staleness, by contrast, **is** detectable without any search: re-rendering the
adapters for the current config and comparing against disk shows the mismatch immediately.

- T5 resolved: reads=config.prompts.dir+on-disk-banners+adapter-contents writes=new-store-tree-only actor=adopter-edits-config-and-deletes/installer-writes interrupt=two-trees-plus-stale-adapters-both-visible-by-content

### T6 Remove the config block

**Question.** What remains discoverable — stated as a limit if the answer is nothing?

**Answer — a recorded limit, and it is narrower than "nothing remains".** Once `prompts` is gone
from `workflow.config.json` there is **no durable pointer**: the config held the only one, and
the alternative — a durable record outside the config — is exactly the state this system chose
not to hold. That limit follows from constraint 1 (the tool may not write the adopter's config,
so it cannot maintain a pointer there) and from the absence of any tool-owned durable file.

**What does not follow is that nothing can be reported.** T5's content signature survives the
config removal and in fact gets easier to apply: with the block gone, `prompts.enabled` falls
back to its default `false`, the current plan produces nothing, and *every* bannered file
trivially satisfies "generated, and not produced by the current plan". A search still has to be
told where to look, and it still misses the unbannered `codex` snippet — but the honest limit is
**"no lookup, only a search"**, not "no report is possible". The broad claim would have told
PRD-034 to skip a capability it can have.

Two consequences the adopter must be told, because neither is inferable:

1. `templates.prd` typically points into the store (`<dir>/templates/prd-template.md`). Removing
   the `prompts` block without clearing that key leaves `gate new` reading a path that may no
   longer exist. **Both edits belong in the same change.**
2. The generated files — store and adapters — remain on disk and remain readable by agents.
   Removing the config deactivates the *plan*, never the *files*. Deleting them is a separate,
   human act.

- T6 resolved: reads=no-pointer-survives-content-search-only writes=nothing actor=adopter-only interrupt=n/a-config-edit-is-atomic-to-this-system

### T7 The receipt's own second write

**Question.** Who writes it, and is it itself a destination?

**Answer — a recorded limit, and the design decision behind it.** **There is no receipt**, and
this model does not introduce one. PRD-029 ships a one-way install that writes nothing but the
generated set, and the question a receipt would answer — *which paths did this tool generate?* —
is already answered per file by the **banner**, which no second write can go stale relative to
because it is written by the same action that writes the file.

A receipt would add exactly one capability the banner cannot: **scope across absence** —
naming a path that was generated once and is no longer produced, so that a report can mention it
without finding it. T4 and T5 are the two transitions that would benefit, and both were answered
above from content instead. The unbannered paths — the `codex` snippet and
`prompts/PLACEHOLDERS.md` (Revision 2) — are the cases where that substitution genuinely
fails rather than merely costing a search: with no banner, content answers nothing about
them once they are unplanned, so they are the paths a receipt would cover and the current
design cannot.

If a later item revisits this, the constraint this model fixes is the one that broke the earlier
design: a receipt is written by **`init` and by nothing else**, and it is **not itself a
destination** — no command may write a receipt for content it declined to place, because that
is how "membership in the receipt" silently became "authority to overwrite". A reporter writes
nothing, including the receipt. That rule is a boundary on any future receipt, not a plan for
one.

- T7 resolved: reads=n/a-no-receipt-exists writes=nothing-by-decision actor=init-alone-if-one-is-ever-introduced interrupt=n/a-single-write-or-none

## Recorded limits

Collected so a reader does not have to reconstruct them, each with the constraint it follows
from:

| # | Limit                                                                | Follows from                                              | Class |
| - | -------------------------------------------------------------------- | ---------------------------------------------------------- | ----- |
| 1 | Activation cannot be machine-recorded; the adopter pastes the block  | C1 — the tool may not write the adopter's config           | design |
| 2 | An interrupted install leaves an unmarked partial set                | the "no marker" half is the T7 decision; the **in-process** half is implementation — `initWorkspace` holds the whole path→content map before it writes, so it could unlink its own just-created paths on a write failure and shrink this to the hard-interrupt case, with no manifest and without touching an adopter's file | mixed |
| 3 | An intentional edit has no representation on disk                    | C1 + no tool-owned durable state                           | design |
| 4 | A removed adapter's file keeps working until a human deletes it      | C2 — no command deletes                                    | design |
| 5 | After a config removal there is no durable **pointer**; a content search still works | C1 + no tool-owned durable state           | design |
| 6 | Absence-scoped reporting is impossible without a receipt; the two unbannered paths — the `codex` snippet and `prompts/PLACEHOLDERS.md` (Revision 2) — are the cases content cannot substitute for, and a banner-stripped file joins them for discovery (never for planned-path byte comparison) | the T7 decision | design |

Set-level atomicity is not available to row 2 by any staged-write trick: the generated set spans
three unrelated destination roots (`<dir>/`, `.claude/commands/`, `.cursor/rules/`), so no single
rename makes the set atomic, and a durable journal across them is a manifest — which is the T7
decision, i.e. the design half. Nor is temp-then-rename a candidate at all: `rename(2)` silently
replaces an existing destination and would break C1's "nothing is ever overwritten", which is
the promise the installer chose `wx` for. **In-process rollback** is the part that is genuinely
implementation-side, and it is what row 2 stands on.

Rows marked `design` are limits of the system as designed: a future item may change the design,
and until it does, it may not report them as bugs against it. Row 2 is **not** one of them —
its in-process half is the implementation's, and a future item is free to report it as a defect
without reopening any decision recorded here. The distinction is stated because the blanket
version of this sentence would have forbidden exactly that.

## Ordering, rollback, and the cost of changing this document

**Ordering.** PRD-034's functional requirements are written against this model, and its §4 is
blocked until an owner acceptance names this file. No partial approval unblocks a subset of
transitions: the FRs are derived from the model as a whole, because the answers interlock —
T2's apply mechanism depends on T3's authority answer, and T4 and T5 both rest on T7's decision
that content, not a receipt, is the basis for discovery.

**Rollback.** This item's undo is a revert of one document commit. There is no adopter state, no
schema, no deploy ordering, and nothing installed anywhere by this change.

**The cost of a later change.** Once PRD-034 exists, revising an answer here invalidates the FRs
derived from it — a change to T3's authority boundary or T7's no-receipt decision invalidates
the largest share, since both are load-bearing for what any reporting command may do. The
correction is then a **superseding revision of this document with its consequences enumerated**,
not an edit in place: an edit in place would leave PRD-034's FRs stating a rule this document no
longer holds, which is the restatement failure both parent items were narrowed to stop.

## Revision 2 — 2026-07-28, awaiting owner approval

**Trigger.** PRD-034's iteration-1 independent readiness score (Codex, 5.1 ITERATE) proved
against the shipped renderer that Revision 1's uniqueness claim is false:
`renderPrompts` copies `prompts/PLACEHOLDERS.md` **verbatim, with no banner**, under a
deliberate `verbatim` disposition (`core/run/prompts.ts:656-661` — the registry documents
the tokens substitution would consume), while `generatedPaths()` includes it in the
generated set. The transcribing session re-verified the claim before this revision was
drafted. Missing Piece 1 of that score requires this supersession before the FRs are
re-derived.

**Statements superseded, old → new, with the section carrying each change:**

1. *Vocabulary → Banner.* "the one file the adopter is expected to paste by hand is the
   one with no provenance at all" → **two unbannered generated paths**: the codex snippet
   and `PLACEHOLDERS.md`, the latter deliberate with its reason in code. Added: the
   detection/attribution split — unbannered **planned** paths remain byte-comparable
   against a fresh render; only stale-versus-modified attribution is lost, and the same
   holds for a banner-stripped file.
2. *T2.* "except for the codex snippet … unknowable" → both unbannered paths are
   version-unattributable in a mixed state; their bytes still compare.
3. *T4 (and by reference T5/T6).* "The second route does not cover the codex adapter" →
   content discovery misses **both** unbannered paths once unplanned; nothing recovers
   them after the producing config is gone.
4. *T7.* "it is the one path a receipt would cover and the current design cannot" →
   they are the **paths**, plural.
5. *Recorded limit 6.* Rewritten to name both paths and to bound the banner-stripped
   case: stripped files leave content discovery, never planned-path byte comparison.

**What Revision 2 does NOT change:** every constraint (1–4), every actor answer, T3's
suppress-but-never-write boundary, T7's no-receipt decision, limits 1–5, and the
design/mixed classification of limit 2. No transition's actor moves.

**Consequences enumerated for PRD-034's re-derivation:**

- The classification over planned paths must be total in three arms — bytes equal;
  diverged with parseable banner (attributable: stale | modified); diverged or
  banner-absent/unparseable (unattributable) — with the two deliberately unbannered
  paths and any stripped file landing in the third arm by construction, never in a
  class requiring a version.
- Orphan discovery claims must be scoped to bannered files inside declared scan roots;
  a check that does not implement a bounded wider search must restate limits 5 and 6
  honestly rather than claim T5/T6 coverage (and limit 5's honest form is "no lookup,
  only a search" — a renamed-away tree is findable only by a search the check must be
  told to run, wherever it is told to look).
- A T6-disabled configuration still leaves the content-search **capability** available;
  a check that exits silently on `enabled: false` must say it is not exercising that
  capability rather than implying nothing is discoverable.
- The `PLACEHOLDERS.md` expected content for byte comparison is the packaged source
  file itself (verbatim disposition): the fresh render already produces it, so no new
  mechanism is needed — only the class assignment above.
